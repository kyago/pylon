# Pylon Cleanup — 세션 마무리

이번 세션의 작업을 마무리합니다. 보통 PR이 머지된 뒤 실행되므로 작업 트리가 깨끗해도 일이 없었던 것이 아닙니다 —
이번 세션에 한 일은 대화 기록과 PR에서 찾습니다.

단계는 순서대로 진행합니다. 브랜치는 머지가 확인된 뒤에만 지웁니다. 이미 없어진 브랜치·워크트리는 "이미 정리됨"으로
보고하고 넘어갑니다.

## Step 1: 세션 범위 파악

각 repo에서 먼저 `git fetch -q origin`을 실행한 뒤, 확인한 근거로만 정리합니다:
- 대화에서 커밋·PR·이슈를 만든 repo와 번호·URL, 사용한 브랜치·워크트리
- 미커밋 변경(`git status`)과 미푸시 커밋(upstream이 있으면 `git log @{u}..HEAD`, 없으면 `git log origin/<base>..HEAD`)

메모리는 프로젝트별로 저장되므로 대상은 `AGENTS.md`의 프로젝트 목록에 있는 이름을 그대로 씁니다. 다른 이름으로
저장하면 `pylon mem search --project <이름>`에 잡히지 않습니다.
- 세션이 여러 프로젝트를 다뤘으면 항목마다 해당 프로젝트에 나눠 저장합니다.
- 프로젝트 목록이 없으면(단일 repo 워크스페이스) 워크스페이스 디렉토리 이름을 쓰고 보고에 밝힙니다.
- 근거가 전혀 없을 때만 사용자에게 대상을 묻습니다.

## Step 2: 검증과 결과 확인

검증은 아직 검증되지 않은 변경에만 실행합니다. 머지된 base 브랜치에서 다시 돌리는 것은 이번 변경에 대해 아무것도
증명하지 않습니다.

- 미커밋·미푸시 변경이 있는 repo(워크트리 포함)는 그 루트에서 저장소의 테스트·린트 명령을 실행합니다. 명령은
  `README`, `Makefile`, CI 설정에서 찾고, 찾지 못하면 "검증 미설정"으로 보고하고 계속합니다. 실패하면 실패 항목을
  보고하고 그 repo의 브랜치 정리는 하지 않습니다.
- 이미 PR로 머지된 변경은 다음을 근거로 씁니다:
  - 이 대화에서 돌린 검증 출력. 검증을 돌린 커밋이 머지된 PR의 head(`gh pr view <번호> --json headRefOid`)와 같을
    때만 근거가 됩니다.
  - PR의 체크 결과(`gh pr checks <번호>`). "no checks reported"는 실패가 아니라 "PR 체크 없음"으로 보고합니다.

세션의 결과물마다 확인한 것과 확인하지 않은 것을 나눕니다. 배포 결과, 마이그레이션 적용, 운영 데이터 반영처럼 코드
밖의 결과는 읽기 전용으로 확인할 수단(배포 run 로그, 조회 쿼리, 상태 API)이 있으면 실제로 조회해 확인하고, 수단이
없으면 "미확인"으로 남깁니다. Step 7 보고에 그대로 씁니다.

## Step 3: 메모리 저장

다음 세션이 모르면 시간을 쓰게 될 것만 저장합니다:
- 방향을 정한 결정과 근거 → `decision`
- 이번에 시간을 쓴 함정·교훈 → `learning`
- 재사용할 패턴 → `pattern`

코드·커밋·PR 본문에서 바로 알 수 있는 사실과 변경 파일 목록 같은 이력은 저장하지 않습니다(검색을 오염시킵니다).

먼저 기존 항목을 확인합니다:

```bash
pylon mem search --project <프로젝트> --query "<주제 키워드>"
```

같은 주제가 있으면 **같은 `--category`와 `--key`**로 저장해 갱신합니다(갱신은 카테고리와 key가 모두 같아야
일어납니다). 본문 첫 줄은 한 줄 요약으로 씁니다 — `INDEX.md`에 그 줄이 보입니다. 핵심 용어는 `Redis(레디스)`처럼
영문·한글을 함께 씁니다.

```bash
pylon mem store --project <프로젝트> --category decision --key <슬러그> --content "결정 요약
근거와 맥락"
```

저장할 것이 없으면 건너뜁니다.

교훈이 테스트나 lint로 강제될 수 있으면 메모리 글만으로 두지 않고 Step 7 보고에 검사 추가 제안을 함께 적습니다 —
어느 repo에 어떤 테스트·lint를 넣으면 같은 실수가 실패로 드러나는지. 여기서는 코드를 고치지 않고 제안만 합니다.

## Step 4: 도메인 지식 갱신

세션이 바꾼 사실이 `.pylon/domain/*.md`나 `<project>/.pylon/context.md`에 적혀 있으면(스펙 버전, 테이블·필드 목록,
흐름, 운영 절차) 머지된 코드에서 확인한 값으로 그 줄을 고칩니다. 새 사실이 그 문서가 다루는 범위면 추가합니다. 코드에서
확인하지 않은 내용은 적지 않습니다. 아직 머지 전이면 건너뛰고 "머지 후 갱신 필요"로 보고합니다.

## Step 5: 머지된 브랜치·워크트리 정리

이번 세션이 만들거나 작업한 브랜치·워크트리만 다룹니다. 그 밖의 브랜치는 후보로만 보고합니다.

**머지 확인.** `gh pr list --head <branch> --state merged --json number,headRefOid`의 PR 중 `headRefOid`가 지금 브랜치 끝
(`git rev-parse <branch>`, 로컬이 없으면 `origin/<branch>`)과 같고, 같은 head로 열린 PR이 없어야 합니다. 이름만 같고
커밋이 다르면 머지되지 않은 것으로 봅니다.

**정리.**
- 워크트리: `git worktree remove <path>` — `--force`를 쓰지 않습니다. 미커밋 변경이 있으면 git이 거부하고, 그 워크트리와
  브랜치는 남깁니다.
- 브랜치가 메인 체크아웃에 체크아웃되어 있고 미커밋 변경이 없으면 base로 전환해 `git pull --ff-only`로 맞춘 뒤 지웁니다.
- 로컬 브랜치: `git branch -D <branch>`.
- 원격 브랜치: `git ls-remote --heads origin <branch>`에 있고, `origin/<branch>`도 머지 확인을 통과할 때만
  `git push origin --delete <branch>`. 원격에 로컬보다 앞선 커밋이 있으면 남깁니다.
- 원격 기본 브랜치(`git symbolic-ref refs/remotes/origin/HEAD`, 설정되어 있지 않으면
  `gh repo view --json defaultBranchRef -q .defaultBranchRef.name`)와 보호 브랜치(`main`, `master`, `develop`, `dev`)는
  건드리지 않습니다. 열린 PR의 base인 브랜치(`gh pr list --base <branch> --state open`이 비어 있지 않음)도 지우지 않습니다.

머지되지 않았거나 머지를 확인할 수 없는 브랜치는 남기고 이유를 보고합니다.

## Step 6: 커밋 안내

워크스페이스가 git 저장소이고 `.pylon/memory/`, `.pylon/domain/`에 커밋되지 않은 변경이 있거나, 프로젝트에 커밋되지
않은 변경이 남았으면 무엇이 남았는지 알리고 커밋을 안내합니다. 자동 커밋하지 않습니다.

## Step 7: 완료 보고

- 결과 확인: 확인한 것(근거)과 미확인 항목
- 저장·갱신한 메모리(프로젝트 · 카테고리 · key, 신규/갱신)
- 검사 추가 제안(교훈 · repo · 추가할 테스트나 lint), 없으면 생략
- 고친 도메인 문서와 바뀐 사실, 또는 머지 후로 미룬 것
- 브랜치·워크트리: 지운 것, 남긴 것(이유)
- 커밋 안내 여부
